# Task planning

Ordinary work proceeds directly. Plan when uncertainty or coordination costs more
than a brief decision. Infer from the request, repository, project DESIGN.md,
local patterns and personal profile before asking.

## Clarification

Ask only when an unanswered choice materially changes design, architecture, scope,
motion or output and guessing risks substantial rework. Prefer one bundled step
with roughly 1–3 important questions. With a sensible low-risk default, choose it.
Do not transfer design responsibility to the user.

When choices are known, offer at most 3–5 short options including free response;
respect a native tool's smaller limit. Mark a recommendation where useful and
include "use your judgment" when helpful. Always allow combining, modifying or
rejecting options and adding context. Native free text satisfies the freeform
option; do not duplicate it. If a UI cannot accept free text, use prose choices
with an explicit custom-answer option.

Example: restrained / balanced (recommended) / expressive / use your judgment /
custom or combination. "Balanced, with restrained density and expressive type"
is a complete answer. Extra context outranks a forced category. Retain decisions
within the task; do not silently turn them into global preferences.

## Large work

Capture a compact goal only when useful:

```text
Goal: Build [thing] in [existing technology].
Requirements: behavior; interaction; responsive/accessibility/performance needs.
Design direction: feel; visual language; context; purposeful motion.
Output: files/location and observable acceptance criteria.
```

Use applicable fields only; this is not a questionnaire. A portable goal is text.
Native /goal or goal tools require client support and authorization. Never invent
equivalent syntax or create a separate user-owned task just to hold a goal.

Default to one agent. Parallelism requires independent scopes, actual savings
after context duplication/integration, and user or applicable client authorization.
Use the minimum useful workers, each with a bounded goal, owned files, constraints
and compact expected result rather than the full transcript. Parent integrates
and verifies. Avoid overlapping edits, duplicate research and automatic reviewers.
Model routing uses supported authorized controls; never silently change model,
provider or billing defaults.

Handoffs retain decisions, state, unresolved risks, next steps and source pointers.
No transcript dump. Plan enough to prevent rework, then build.
